# Backend Phase 1: persistent farmer and farm records

## Implemented boundary

The Streamlit app remains operational and a React/TypeScript app runs alongside it. Both use the same FastAPI service/database when configured; neither opens SQLite directly. In local development, Streamlit defaults to `http://127.0.0.1:8001`; set `CROP_PULSE_API_URL` to override it. Production requires an explicit API URL and fails closed without one. React is the only password sign-in and registration interface. Streamlit requires a valid account session before displaying protected pages; if the session is absent it links to React sign-in and returns to Streamlit through a short-lived one-use handoff. Its profile shows the server account and, for farmers, provides farm selection/creation and sign-out. Farm, crop-plan, and activity resources are owner-scoped by FastAPI; temporary Streamlit entries are cleared at sign-out. React uses a 30-minute HttpOnly browser cookie plus signed CSRF token. See [React setup](react-app-setup.md) for deployment path routing, Windows commands and [Phase 2 verification](phase-2-verification.md) for port details.

### Ownership and permissions

- Registration creates a `Farmer` profile. Account creation stores a versioned acceptance timestamp for the displayed prototype data notice.
- A farmer can list/create only their own farms. Each farm has exactly one owner; all farm, plan, and activity endpoints require an active farmer session and check ownership server-side.
- Looking up another user's farm returns the same `404` response as an unknown farm. Unauthenticated requests receive `401`.
- Roles are `farmer`, `reviewer`, and `admin`, with account states `active` or `suspended`. Registration always assigns `farmer`; an explicit interactive local operator command provisions the first administrator. Authenticated administrators may assign reviewer/admin permissions and district scope. No shared farm access is implemented.
- Passwords use Argon2 hashes through `pwdlib`; HS256 tokens expire after 30 minutes and have a server-side session row. Streamlit bearer tokens remain in server-side Streamlit session state. React session tokens are in an HttpOnly, host-only, SameSite=Lax cookie; cookie-authenticated writes require a signed CSRF token. `POST /v1/auth/logout` or `/v1/browser-auth/logout` revokes the server session.
- Login, registration, password recovery, email changes, and deletion attempts use database-backed hashed IP/email rate buckets. They are a basic application layer, not a replacement for gateway rate limits. Registration email verification and MFA are not implemented. Password recovery and email change require API-side SMTP configuration. Use only for local development or a controlled pilot after security and privacy review.

### Database model

| Table | Main fields and relationship |
| --- | --- |
| `farmers` | Email (unique), display name, Argon2 hash, privacy notice version/acceptance time, role and active/suspended status |
| `farmer_sessions` | JWT session identifier, owner, expiry and revocation time |
| `farms` | Owner farmer, name, Rwanda district, optional sector and area |
| `farm_fields` | Field name and owner farm, optional area in hectares and farmer-supplied coordinates, archive and timestamps |
| `crop_plans` | Owned farm, optional field, district, crop, season, planned planting date, optional actual planting date, area, serialized plan, provisional verification, lifecycle status |
| `crop_plan_evidence` | Optional plan-linked claim/source/applicability/date/period/units/confidence/limitations and dataset/recommender provenance snapshot; no recommendation data is currently generated by the React plan form |
| `farm_activities` | Owned farm, district, crop, season, activity kind/date, optional area/quantity/unit/cost, notes, user-reported status |
| `reviewer_districts` | Reviewer account and each district the reviewer may access |
| `activity_review_decisions` | Immutable reviewer, decision, reason, and timestamp for a submitted activity; original facts remain unchanged |
| `admin_audit_events` | Actor, target, action, reason, result, and timestamp for privileged actions |
| `auth_attempts` | Hashed rate-limit buckets and timestamps; no raw IP or email is stored |
| `account_action_tokens` | Hashed, expiring, single-use email-change and password-reset tokens; raw tokens are sent by email and never stored |
| `messaging_settings` | Singleton administrator-controlled private farmer-to-reviewer messaging switch; starts disabled |
| `private_conversations` | Unique farmer/reviewer pair, accessible only while both accounts and current district eligibility remain valid |
| `private_messages` | Participant-authored text, server timestamp, persisted read timestamp, conversation/account cascade |
| `crop_health_cases` | Farmer-owned private crop-health report, farm and optional field/plan references, symptom context, normalized image BLOB, optional experimental model-screening result, lifecycle and provisional observation state |
| `crop_health_case_updates` | Private append-only reviewer/farmer updates, action, optional provisional assessment, author and timestamp |

IDs are opaque UUIDs. Foreign keys cascade on account/farm deletion at the database level. Farm activity edits and deletes are restricted to a farm the current farmer owns. Saved crop plans remain provisional; saving one also creates a corresponding “Seasonal plan” activity within the same transaction.

### API

- `POST /v1/auth/register`, `POST /v1/auth/login`, `GET /v1/me`
- `POST /v1/auth/logout` revokes the current session; the Streamlit client also clears local authentication state.
- `GET /health` checks database connectivity and returns a sanitized unavailable response if the database is down.
- `GET/POST /v1/farms`, `GET/PUT/DELETE /v1/farms/{farm_id}`
- `GET/POST /v1/farms/{farm_id}/activities`
- `PUT/DELETE /v1/farms/{farm_id}/activities/{activity_id}`
- `GET/POST /v1/farms/{farm_id}/plans`; `PATCH /v1/farms/{farm_id}/plans/{plan_id}/status` (owner-scoped lifecycle transitions)
- `/v1/messaging/*` private text conversations, eligible reviewer discovery, paginated history, explicit read updates, and unread counts; the global switch is admin-only at `/v1/admin/messaging-setting`. See [private messaging Phase 1](private-messaging-phase-1.md) for permission checks and limitations.
- `/v1/crop-health/*` private report creation, farmer case history and authorized photo delivery; `/v1/reviewer/crop-health/*` district-scoped reviewer queue and private case updates. Access is recalculated from active account status, farm ownership and reviewer district assignments. Uploads are decoded/re-encoded, size-limited, metadata-stripped and stored privately in the relational database. Maize photos can receive experimental model-ranked candidates, but the result is neither a diagnosis nor treatment advice. See [crop-health reporting](crop-health-review.md) and [model limits](crop-disease-model.md).
- `GET /docs` provides the local OpenAPI reference.
- `GET /v1/admin/overview`, `GET /v1/admin/farmers`, audited status/role/session/scope actions, and `GET /v1/admin/audit-events` require administrator role.
- `GET /v1/reviewer/activities` and `POST /v1/reviewer/activities/{id}/decisions` enforce reviewer district assignments; admins may review any saved farm activity.
- `GET /v1/browser-auth/csrf` and browser login/register/logout provide a separate cookie session for React. Browser routes also support confirmed email changes, password recovery/reset and password-confirmed self-service account deletion. CORS origins are an explicit environment allowlist.

The API validates email, season, known Rwanda districts and supported crop names, text lengths, positive farm/plan area, and nonnegative reported measurements. Farmer reports remain user reported after a review decision; review decisions are append-only and do not verify underlying facts. Saved plans remain provisional and start in `planned`; status transitions are `planned → planted → monitoring → harvesting → completed`, with `planned → cancelled` also allowed. Marking a plan `planted` requires a nonfuture actual planting date and atomically creates one user-reported planting activity without assuming the full planned area was planted. Repeating an identical transition is idempotent. The dashboard's demonstration dataset remains in its existing data loader and is not inserted into the farmer database or used as a farmer's records.

Self-service email changes require current-password reauthentication and confirmation at the new address; confirmation revokes existing sessions. Password recovery uses generic responses to avoid confirming whether an email is registered, and tokens expire after 30 minutes. Successful reset revokes all sessions. Configure SMTP on the API using `CROP_PULSE_SMTP_HOST`, `CROP_PULSE_SMTP_PORT`, optional username/password, `CROP_PULSE_SMTP_FROM`, TLS settings, and `CROP_PULSE_PUBLIC_APP_URL`. The Python standard-library SMTP client is used; no email vendor or paid service is bundled. Account deletion requires the current password and typing `DELETE`; it removes the account's farms/plans/activities/sessions, preserves immutable review decisions while setting the deleted reviewer identity to null, preserves a minimized deletion audit event, and prevents deletion of the last administrator. Registration email verification remains outside this implementation.

## Session-only frontend entries

| Entry | Existing frontend operations | Phase 1 status |
| --- | --- | --- |
| Farm records | Create, list/filter, update, delete, summary and CSV export | Persisted for a signed-in farmer and selected farm |
| Crop plans | Generate in session, view, download; save as a seasonal-plan record | Saved plans persisted for signed-in farmer; generated unsaved plan stays in session |
| Market quotes | Create, list/filter/chart, delete, export | Still session-only |
| Guidance review submissions | Create, list, export | Still session-only; not authenticated or an approval |
| Recommendation feedback | Create, list, export | Still session-only |
| Pest reports | Create, list, export | Still session-only and unverified |
| Extension visit notes | Create, list, export | Still session-only; no officer role |
| Cooperative activities | Create, list, export | Still session-only and aggregate only |
| Weather observations | Create, list, export | Still session-only and unverified |

Navigation/filter/language state, current planner form values, generated unsaved crop plan, and recommendation feedback context are also in Streamlit session state. They are UI state, not durable farmer records. Market, review, feedback, pest, extension, cooperative, and weather entries remain temporary and are cleared at sign-out boundaries. `Clear session entries` clears current-session entries; it does not delete records in the database. Streamlit does not accept passwords or create accounts; users authenticate in React, and Streamlit verifies the same API account session and role.

## Local setup

Use the complete Windows PowerShell instructions in [React app setup](react-app-setup.md). They cover isolated Python/npm environments, backup verification, database migrations, API health, first-admin provisioning, React startup, and authenticated Streamlit access. Do not point Alembic at the legacy `data/croppulse_local.sqlite3` file.

For local development and production, configure a securely generated server-side signing key before starting the API. Startup now fails with a configuration error when it is missing, too short, a placeholder, or obviously weak; it is never generated or defaulted by the API. Generate one for local development with `python -c "import secrets; print(secrets.token_urlsafe(48))"`. Keep it in the API process environment only. Restarting with a new key signs out existing users. For an intended PostgreSQL deployment, provision a private database and least-privilege database user first. Set these server-side values on the API process:

```text
CROP_PULSE_DATABASE_URL=postgresql+psycopg://USER:URL_ENCODED_PASSWORD@HOST:5432/DATABASE
CROP_PULSE_SECRET_KEY=<random secret, at least 32 characters>
```

Set only `CROP_PULSE_API_URL=https://your-private-api-host` on the Streamlit process. Do not pass the database credentials or JWT signing key to the UI process.

Percent-encode reserved characters in the database URL. Apply schema changes with `alembic upgrade head`; do not enable `CROP_PULSE_AUTO_CREATE_SCHEMA` outside isolated development. Never put real secrets in source control, Streamlit client-visible configuration, or screenshots. The local SQLite database is ignored by Git.

## Migrations, backups and operations

- Alembic migrations currently run from `0001_phase1_records.py` through `0011_crop_health_ai_screening.py`; `alembic upgrade head` applies pending revisions. Migration 0006 adds private messaging; 0007 adds farmer-owned fields/evidence; 0008 adds the Streamlit handoff; 0009 adds private crop-health reports and reviewer updates; 0010 adds optional affected-plant-parts and spreading context; 0011 adds optional model-screening metadata without changing existing reports. Back up before applying migrations; see [React setup and recovery](react-app-setup.md). Migration testing uses disposable SQLite databases; a live PostgreSQL migration is not verified here.
- For PostgreSQL, schedule and monitor encrypted `pg_dump` backups, restrict backup access, test restores, and set retention with the data owner. For local SQLite only, stop writers before copying `data/croppulse_phase1.sqlite3`; that file is not a production backup strategy.
- Keep the API on a private network behind TLS before any remote use. Configure network restrictions, secret rotation, database encryption/managed disk encryption, audit logging, rate limiting, monitoring, incident response and retention/deletion policy before a pilot handling real farmer data.
- No migration/import of prior anonymous session data is performed. Existing session data has no verified account owner; farmers must re-enter data under their own account if appropriate.

## Still outside this phase / release checklist

No live market provider, notifications, AI features, background jobs, national aggregates, cross-farm sharing, registration email verification, MFA, audit trail for ordinary reads, or legacy-session migration is included. SMTP must be configured to use email change and password recovery. Privacy notice/legal review, consent and retention policy, managed database provisioning, operational security, accessibility/device review, agronomic review, backup-restore drill and a controlled farmer pilot remain before any public launch. Passing automated checks alone does not make this application production-ready.
